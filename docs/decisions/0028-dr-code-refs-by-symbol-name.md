# DR のコード参照はシンボル名で指す

## Context and Problem Statement

DR がコードを指すとき、ファイル名にコロンと行番号を続ける形で書いていた。コードが動くと参照先がずれ、ずれたことが読者に見えない。行番号の先には別の宣言があるので、参照は「間違っている」ではなく「別のものを指している」状態になる。

adrift (`docs/audit/2026-08-16-155753-dr-drift.md`) が挙げた 105 件のうち約 30 件がこの形だった。番号を直しても、次にコードが動いた時点で同じ件数が再び上がる。実際 PR #432 と #433 が `src/lib.rs` へ約 80 行を足したため、レポート自身の行番号も出た時点でずれていた。

DR-0014 は自分の中和点表の中でこの問題を先に解いている。

> 場所はファイルまでとし、行番号は書かない。行番号はこの表の外の変更で古くなり、古いことが誰にも見えない。関数名は `ugrep -F 'fn <name>'` で一意に引ける。

その方針が 1 つの表の中だけに閉じていた。

## Decision Drivers

- DR を根拠に実装の意図を読む人が、参照先を自力で探し直さずに済むこと。
- 参照が古くなったとき、古いことが検出できること。行番号は静かに別のものを指す。
- 制定時の状態を記録した箇所と、現在のコードを指す箇所を、読者が区別できること。

## Considered Options

- 方式 A: 参照をシンボル名で書き、行番号を書かない。
- 方式 B: 行番号を書き続け、定期的に一括で更新する。
- 方式 C: 参照を DR から外し、コード側の `ADR-00NN` コメントだけを索引にする。

## Decision Outcome

Chosen option: 方式 A。DR がコードを指すときは、ファイル名とシンボル名の 2 つ組で書く。行番号は書かない。

指す対象は次の優先順位で選ぶ。

| 順位 | 対象                         | 使う場面                                      |
| ---- | ---------------------------- | --------------------------------------------- |
| 1    | テスト id (`[T-FC038]`)      | その振る舞いを pin するテストがある           |
| 2    | シンボル名 (`get_json_once`) | 関数、定数、struct、field、doc comment を指す |
| 3    | 節見出し                     | 単一のシンボルへ落ちない範囲を指す            |

テスト id を先に置くのは、id が `src/test_support.rs` の採番規約で管理されており、リポジトリ全体で一意だからになる。シンボル名はファイルをまたぐと重複するので、ファイル名を必ず併記する (`classify` は 3 ファイル、`should_check_https` は 2 ファイルにある)。

外部 crate を指すときは版つきパスを保つ (`htmd-0.5.5 の src/text_util.rs` の `collapse_whitespace`)。版が変わればパスごと解決できなくなり、そのことが読者に見える。

### 例外: 制定時の位置の記録

制定時に何がどこを指していたかを記録する文は、行番号をそのまま残す。現在のコード位置ではないので、シンボル名へ書き換えると記録が意味を失う。

この例外に当たる文は日付を伴う。DR-0011 の `## Context and Problem Statement` にある 2 箇所が唯一の実例で、段落が「2026-05-19 時点で」で始まる。

| DR   | 箇所                                       | 対象                                                           |
| ---- | ------------------------------------------ | -------------------------------------------------------------- |
| 0011 | `## Context and Problem Statement` の 1 文 | `src/envelope.rs` の 1 箇所と `src/tools/errors.rs` の 11 箇所 |

### Consequences

- Good, because コードが動いても参照は解決できる。シンボルを消したときは `ugrep` が 0 件を返し、参照が壊れたことが見える。
- Good, because 参照を読む人が行番号を数える必要がなくなる。
- Bad, because シンボルを rename すると参照は静かに古くなる。行番号との違いは、検出できる点だけになる。
- Bad, because 単一のシンボルへ落ちない範囲は節見出しで指すので、元の行範囲より広い対象を指すことになる。

### Confirmation

残存は次の grep で測る。上の例外表が挙げる DR-0011 の 2 match だけが残り、それ以外は 0 件になる。この DR 自身は参照の形を文で述べるので、grep には当たらない。

```sh
grep -rEo '[A-Za-z0-9_./-]+\.(rs|md):[0-9]+|[^A-Za-z0-9_./-]:[0-9]+-[0-9]+' docs/decisions/
```

後半の選択肢は、ファイル名を省いてコロンと行範囲だけを書く継続参照を拾う。前半だけでは取りこぼす。IPv6 リテラル (`[::1]`) は範囲を持たないので当たらない。

この grep は `README.md L158` の形を拾わない。DR-0010 に 5 行残っており、別の形として扱う。

2026-08-18 時点で 0011 の 2 match のほかに 43 match が残る。対象は 0001、0003、0007、0013、0015、0016、0019、0025、0026 の 9 ファイルで、本文と実装の食い違いを直す変更と同じ単位で書き換える。

## Pros and Cons of the Options

### 方式 A: シンボル名で書く (採用)

- Good, because コードが動いても参照が解決できる。
- Good, because DR-0014 が自分の表で既に採っており、形が実証済み。
- Bad, because rename には追随しない。

### 方式 B: 行番号を書き続け、定期的に一括更新する

- Good, because 参照が指す範囲が最も狭い。
- Bad, because 更新の間隔がそのままずれの寿命になる。adrift の 1 回が 83 agent/78 分かかるので、間隔は短くできない。
- Bad, because ずれている間、古いことが読者に見えない。

### 方式 C: DR からコード参照を外す

- Good, because 参照が古くなる経路そのものが消える。
- Bad, because DR がファイル内の特定の 1 箇所を指し分けられなくなる。`src` の `ADR-00` コメント 130 行は、どの DR かを示すだけで逆向きには引けない。

## More Information

### Reassessment Triggers

- シンボルの rename で参照が壊れる件数が、行番号のずれの件数を超えたとき。
- `ugrep` が参照先シンボルの実在を検査する CI job が入り、方式 B の「ずれが見えない」欠点が解消されたとき。
- 例外表の行数が増え、日付を伴う文かどうかの判定が 1 行で済まなくなったとき。
