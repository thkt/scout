# Fetch Body Line-Break Handling: Paragraph Folding as Contract, `<br>`/`<pre>` as the Named Exceptions

## Context and Problem Statement

fast_html2md 0.0.62 から htmd 0.5.5 への置き換え (#373) で、段落の改行の扱いが変わった。旧ライブラリは原文の改行をそのまま残していたが、新ライブラリは段落内の折り返しを空白 1 個へ畳む。fetch が返す本文のほぼ全ページでこの差が出力に現れるが、畳みを正とするかどうかを決定した DR はこれまで無かった (#377)。

畳みを正とする根拠は、変換ライブラリの選定そのものにはない。旧ライブラリが残していた改行は HTML ソースの整形であって文書構造ではなく、旧ライブラリは段落境界に空行も出さないため、原文の改行を残す方向を選んでも段落構造自体は再現できない。CommonMark 0.31.2 §6.8 は softbreak (段落内の折り返し) をレンダラの裁量で改行かスペースのどちらに変換してもよいと定めており、この裁量が畳みを許す。

ブラウザの表示結果を根拠に置くことはできない。CSS Text 3 §4.1.3 Segment Break Transformation Rules は segment break を空白へ変えるか除去するかを UA-defined と定め、規範外の例で中国語について「joining the two lines with no intervening space」と示している。同じ節の Note は、歴史的に HTML と CSS が segment break を無条件に空白へ変換してきたと書き、UA の heuristics が保守的である必要を述べる。つまり現行ブラウザの慣行は畳みの側にあるが、仕様の意図は CJK で空白を入れない側にある。

判断を保留し、改行の扱いを書かないまま進める案もあるが、この場合、次に変換ライブラリへ触れるたびに同じ問いを立て直すことになる。この DR は、fetch が返す本文の改行の扱いを契約として固定し、契約に含めない形を既知の限界として切り分ける。

## Decision Drivers

- OUTCOME: 一次ソース本文を AI エージェントの context に届ける。改行の扱いが変換ライブラリの入れ替えのたびに無定義のまま変わると、下流の再現性が損なわれる
- CommonMark 0.31.2 §6.8: softbreak の改行/スペース変換はレンダラの裁量であり、どちらを選んでも文書の意味は変わらない
- 段落構造の再現性: 原文の改行をそのまま残す案は、段落境界に空行を持たない入力に対して段落構造そのものを再現できない
- 実装コスト: 現在の変換経路はテキストノードを読み取る走査の中で折り返しを畳んでおり、要素単位のハンドラ登録という公開の拡張点はこの走査より後段にある

## Considered Options

- 方式 A: 段落内の折り返しの畳みを契約として受け入れ、段落内の `<br>` と `<pre>` の非畳みを契約に加える。表セル・リスト項目・見出しの中の `<br>` は契約から外れる既知の限界として書き分ける (採用)
- 方式 B: 原文の改行を残す方向へ変換経路を作り直す
- 方式 C: 判断を保留し、改行の扱いを DR に書かないまま進める

## Decision Outcome

Chosen option: 方式 A。fetch が返す本文の改行の扱いを次の 3 契約に固定する。

1. 段落内の折り返しは空白 1 個へ畳む
2. 段落内の `<br>` は行末空白 2 個 + 改行の hard break として残す
3. `<pre>` の中身は畳まず、原文の改行をそのまま残す

この 3 契約は T-FC041〜T-FC043 が固定する。「1 段落 1 行」という単純化した書き方はしない。`<br>` を含む段落は契約 2 により複数行になるため、この書き方は偽になる。

表セル・リスト項目・見出しの中の `<br>` はこの契約から外れる既知の限界として扱う。これらの文脈では `<br>` は畳まれて改行を失うか、元の hard break の形を保てず別の形 (インデント付き改行、見出し外の裸行) になる。T-FC045〜T-FC047 がこの 3 形を反例として固定し、対応する変換経路が変わったときにこの DR の記述との食い違いを検出する。

原文の改行を残す方向 (方式 B) へ戻る案は到達できない。段落内の折り返しの畳みは、現在の変換経路がテキストノードを読み取る走査そのものの中で起き、この走査は畳むかどうかを切り替える設定を受け取らない。要素単位のハンドラ登録という公開の拡張点は、この走査より後段で個々の要素の変換結果を差し替えるためのものであり、走査そのものより前段には介入できない。段落用のハンドラを登録して受け取る内容を確認しても、既に畳まれた後の文字列しか渡ってこない。原文の改行を残す手段として残るのは、変換ライブラリ自体を fork して走査部分を書き換えるか、HTML を変換に渡す前に改行を `<br>` へ置換して soft break を hard break に変えるかのどちらかであり、どちらも本 DR の変更範囲を超える (fork のコストは DR-0025/DR-0026 が既に見送った判断と同じ)。

判断を保留する案 (方式 C) は、次に変換ライブラリへ触れるたびに同じ問いを立て直すコストを残すため見送る。

### Consequences

- Good, because 改行の扱いが契約として文書化され、変換経路や変換ライブラリを差し替える際に何を保つべきかの基準が残る
- Good, because 契約に含めない 3 形 (表セル・リスト項目・見出しの中の `<br>`) を既知の限界として明示することで、「1 段落 1 行」のような偽の単純化を避けられる
- Bad, because 段落内の折り返しを畳む理由が変換経路の走査構造に依存しており、原文の改行を残したいという要望が来ても、この DR の変更範囲では応えられない。応えるには変換経路自体を作り直す必要がある
- Bad, because 表セル・リスト項目・見出しの中の `<br>` は契約の対象外のまま残るため、これらの文脈で `<br>` を使うページの本文は、この DR の後も改行が失われたまま届く
- Bad, because CJK の段落では畳みが原文に無い空白を 1 個増やす (#407)。改行が語の区切りの意味を持たない書記体系では、畳みが可視の差になる。実測は ja Wikipedia の 1 ページで 14 箇所/7 行、MDN ja の 1 ページで 0 箇所 (#377 の調査)。解消の経路は存在する。変換前の DOM でテキストノードの改行を、`pre` と `code` の部分木を除いて落とせば、htmd の `compress_whitespace` が空白へ畳む前に消える。区別の対象が空白ではなく改行文字なので、原文に元からあった空白と畳みで生じた空白を取り違えない。この経路のコストは未実測であり、今は払わない

### Confirmation

T-FC041〜T-FC044 (`src/fetch/converter.rs` の `mod tests`) が、段落内の折り返しの畳み、段落内の `<br>` の hard break、`<pre>` の非畳み、inline code 内の連続空白の保持を assert する。T-FC045〜T-FC047 が、表セル・リスト項目・見出しの中の `<br>` がこの契約から外れる 3 形を反例として assert する。`cargo nextest run --profile ci` が緑であることを確認する。

## Pros and Cons of the Options

### 方式 A

段落内の折り返しの畳みを契約として受け入れ、段落内の `<br>` と `<pre>` の非畳みを契約に加え、契約から外れる 3 形を既知の限界として書き分ける。

- Good, because CommonMark の softbreak 規定と整合し、変換経路の現在の挙動をそのまま契約にできる
- Good, because 契約と限界を分けることで、「1 段落 1 行」のような偽の単純化を避けられる
- Bad, because 表セル・リスト項目・見出しの中の `<br>` について、契約を満たす経路を新たに作るコストは残ったまま先送りになる
- Bad, because CJK の段落で原文に無い空白が増える形も、限界として先送りになる

### 方式 B

原文の改行を残す方向へ変換経路を作り直す。

- Good, because HTML ソースの改行がそのまま出力に残り、置き換え前の旧ライブラリと近い見た目になる
- Bad, because 折り返しの畳みは走査そのものの中で起き、要素ハンドラの登録という拡張点はこの走査より後段にあるため、現在の変換経路の上では実現できない
- Bad, because 旧ライブラリも段落境界に空行を出さないため、原文の改行を残しても段落構造そのものは再現できない

### 方式 C

判断を保留し、改行の扱いを DR に書かないまま進める。

- Good, because 今すぐの作業コストが最小で済む
- Bad, because 次に変換ライブラリへ触れるたびに同じ問いを立て直すことになり、判断の蓄積が残らない

## More Information

### Trade-offs

契約を「畳む段落」「hard break を残す段落内の `<br>`」「畳まない `<pre>`」の 3 形に絞ったことで、表セル・リスト項目・見出しの中の `<br>` は既知の限界のまま残る。これらの文脈で `<br>` の hard break を保ちたいという要望が来た場合、対象の変換関数ごとに個別の後処理を足すか、変換経路自体を見直すかの判断が別途要る。

### Reassessment Triggers

- 契約の畳み・hard break・非畳みを判定する変換関数の呼び出しが 2 箇所目になる。単一箇所への直接 assert だけでは複数箇所間の契約の一貫性を保証できなくなるため、共通化を検討する
- 変換ライブラリを替える。折り返しの畳みが走査構造に依存するという Decision Outcome の前提ごと変わるため、3 契約と 3 限界を新しいライブラリの挙動に対して立て直す
- 表セル・リスト項目・見出しの中の `<br>` について、hard break を保ちたいという要望が来る。既知の限界として残すか、契約に格上げして変換経路を作り直すかを判断する
- この DR が引用していない仕様 (CSS, HTML, GFM) が、この DR の根拠文と食い違うと分かる。#407 の CJK の空白増は既存の 3 trigger のどれにも当たらないまま根拠文の書き換えを要求した

Related to issue #377 and #407.
